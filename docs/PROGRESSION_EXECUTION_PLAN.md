# Progression execution plan v1

> Historical Tail Key / cave-entry plan. Active work now follows [House → Boss Door](HOUSE_TO_BOSS_DOOR_PLAN.md). The original gates and evidence below remain unchanged.

Confirmed scope: build cumulative gameplay competence through a continuous Tail Key acquisition and Tail Cave entry, then establish reliability and useful inheritance. This plan replaces reactive cliff optimization as the active work sequence. Keep historical harnesses, policies, data and reserved evaluations intact. No new optimizer run starts before a measured skill blocker and its bounded experiment protocol exist.

## What counts as success

A qualifying episode physically obtains the Tail Key, opens the Tail Cave entrance, and reaches indoor A/map 00/room 17 alive with the transition settled. Acquisition, opening and entry are separate latched events, backed by a continuous physical-button trace. Initial key possession, an already opened entrance or initial entrance-room state disqualify a fresh quest attempt. No inventory writes, powder grants/refills, mid-episode state loads or human rescue. Read-only structured RAM senses, source-grounded quest hints and supplied map/artwork assistance are explicitly labeled. This is guided progression, not zero-shot or pixel-only play.

First prove the post-sword journey; then the supplied house start including sword. The house starts with a shield and is not a power-on/new-game claim. Damage is permitted for first success; death is not. Raw damage, healing, final health and resource consumption remain visible.

## Architecture and staged capability coverage

Physical control is below local skills; the planner selects subgoals using episode state and world memory. The memory stores observations, confidence and conditions, not mutable possession inherited between episodes. Start with room connections and source-grounded quest hints. Treat map artwork as prior reference; validate coordinate alignment and directed physical transitions. Failure to move is an observation, not proof of collision.

Frame-level event evidence includes health loss/gain, inventory/equipment changes, quest flags and dialogue identity. Readable observations describe evidence without claiming causes such as an urchin hit unless attribution is validated. Exact NPC text requires a verified decoding/capture path; an identifier is not a quote. Rank journal entries by progress relevance and novelty after event correctness is established.

Basic sword, shielding/retreat, facing, dialogue, physical equip and powder precede optional spin attacks, bombs and arrows. Each action skill must expose success/failure and a budget. Longer trading sequences use the same request → possession → exchange → verified result machinery established by the witch interaction. Recognition of game mode, action completion, health/resource decisions and recovery belong in the planner/skill interface.

## Generations and evaluation

Version policy weights, world-memory snapshots, planner code and evaluation results separately. Workers consume immutable starting snapshots and append evidence independently. Merge discoveries deterministically between batches; do not let one worker silently change another's live beliefs. Preserve rejected hypotheses and corrections. A better memory and a better controller are separate claims.

Every failed run identifies the first blocker as observation/detector, missing knowledge/prerequisite, planning/route, physical execution, combat/resource or harness failure, with evidence and the furthest completed milestone. A run with useful discoveries can fail the quest; report both outcomes.

## M3 Ultra resource policy

Use one worker until stage 1 passes. Benchmark the new stage-3 workload at 8/16/24/32 workers on the same 32 development episode specifications, maximum 256 decisions each, one numerical-library thread per worker, actual logging enabled. Select the smallest within 10% of peak successful throughput. Previous collection measured 24 workers at 6,624 actions/s and 32 at 7,072; these are not progression throughput promises. Keep at least 32 GiB available RAM and 100 GiB disk free at dispatch. Stop dispatch on repeated worker failure (3 in a batch), memory/disk limit or declared experiment cap; allow bounded in-flight episodes to drain.

Run one optimizer job at a time. Benchmark CPU against MPS on the actual model/dataset before choosing a device, including synchronization and end-to-end time; verify numerical behavior and checkpoint/resume on the selected backend. Existing CPU-only verified checkpoint machinery must not be silently used to claim MPS resume. RAM holds useful replay and caches, not an allocation target. Record compact events/observations continuously and video for proof/diagnostic runs. No local LLM is necessary for initial event sentences; assess dialogue reasoning later with matched outcomes.
